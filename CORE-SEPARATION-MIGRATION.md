# Synapse — Core Separation Migration

## Роль и контекст

Ты — профессиональный AI-инженер, выполняющий пошаговую миграцию проекта Synapse. Твоя задача — постепенно преобразовать единое web-приложение в платформу, состоящую из нескольких независимых приложений с общей кодовой базой, без потери текущей функциональности.

Конечное состояние структуры проекта:

```
apps/
    web/
    desktop/
    backend/

packages/
    core/
    ui/
    features/
    api/
    shared/
    sync/
```

**Назначение директорий:**

- **core** — полностью платформонезависимая бизнес-логика.
- **web** — браузерное приложение.
- **desktop** — Electron-приложение с локальным хранением данных и синхронизацией.
- **backend** — серверное приложение.
- Все платформы используют единый `core`.

---

## Главные принципы миграции

Строго соблюдай следующие правила на протяжении всей работы:

1. **Никаких больших переписываний:** Не выполняй массовый рефакторинг. Каждая сессия (задача) должна выполнять небольшую, законченную часть работы.
2. **Поведение не меняется:** Нельзя менять бизнес-логику. Изменения касаются исключительно архитектуры. Если нужно изменить поведение — это отдельная задача.
3. **Не ломать историю:** Предпочитай перенос файлов, перемещение модулей и изменение импортов полному переписыванию. Не создавай новый код там, где можно использовать существующий.
4. **Стабильность после каждой задачи:** После любой задачи проект обязан: успешно собираться, проходить `typecheck`, проходить `lint`, иметь полностью рабочее текущее поведение.

---

## Архитектурные правила

1. **Изоляция Core:** `core` не должен зависеть от платформ. Запрещены любые зависимости от: React, Next.js, Browser API, Electron API, Node API, DOM, `window`, `document`, `localStorage`, `cookies`, прямого использования `fetch`.
2. **Dependency Injection:** `core` работает только через абстракции (например, `ContentRepository`, `StorageProvider`, `SyncProvider`, `AuthProvider`). Конкретные реализации находятся вне `core` (в приложениях или адаптерах).
3. **Границы платформ:** Весь платформенный код должен жить исключительно в `apps/` или адаптерах.

---

## Порядок миграции

Работа выполняется строго в следующем порядке. Не перепрыгивай через этапы:

- **Этап 1:** Подготовка монорепозитория (создание структуры `packages` и `apps`, настройка `tsconfig`, `exports`). Ничего не переносить.
- **Этап 2:** Перенос типов, констант, схем, утилит, общих helper-функций.
- **Этап 3:** Перенос бизнес-моделей (Content, Collection, Note, User).
- **Этап 4:** Перенос сервисов (ContentService, SearchService, CollectionService).
- **Этап 5:** Вынесение интерфейсов (StorageProvider, SyncProvider, ContentRepository).
- **Этап 6:** Подключение Web через Core.
- **Этап 7:** Подготовка Desktop.
- **Этап 8:** Подготовка Backend.
- **Этап 9:** Подключение синхронизации.

## Протокол выполнения задачи

### 1. Перед внесением изменений

- Прочитай файл `MIGRATION_WIKI.md` (создай его, если не существует) для понимания текущего контекста.
- Определи цель текущей задачи.
- Определи затрагиваемые файлы.
- Оцени риски и зависимости.
- Убедись, что задача самостоятельна. Если она слишком большая — разбей её.

### 2. Правила переноса файлов

Перед переносом файла определи:

1. От чего он зависит.
2. Может ли он использоваться одновременно в web, desktop и backend.
   Если да — переноси в `packages/`. Если нет — оставь на текущем месте до следующего этапа.

### 3. После завершения задачи

- Исправь импорты.
- Удали мёртвый код.
- Проверь отсутствие циклических зависимостей.
- Убедись, что архитектура стала проще.
- Убедись, что проект собирается и проходит проверки.

## Управление архитектурным долгом (Architecture Debt)

Если во время работы ты обнаруживаешь место, которое нарушает целевую архитектуру, но исправление не входит в текущую задачу, **категорически запрещено** исправлять его "заодно".

Вместо этого добавь запись в файл `ARCHITECTURE_DEBT.md` (создай, если не существует) со следующим форматом:

- **Описание проблемы:** Что нарушает архитектуру.
- **Причина:** Почему это было обнаружено и почему не исправлено сейчас.
- **Предлагаемое решение:** Как это нужно исправить в будущем.
- **Приоритет:** High / Medium / Low.

## Ведение Wiki (MIGRATION_WIKI.md)

После завершения каждой законченной задачи обновляй файл `MIGRATION_WIKI.md`. Это позволит любому агенту продолжить работу спустя недели без изучения истории PR.

**Обязательные разделы Wiki:**

1. **Current architecture:** Текущее состояние структуры проекта.
2. **Migration progress:** Что завершено, что в процессе, что осталось.
3. **Decisions:** Все архитектурные решения. Для каждого: что изменено, почему принято именно это решение, какие альтернативы рассматривались.
4. **Known limitations:** Временные ограничения. Что пока невозможно перенести, почему, и что потребуется сделать позже.
5. **Next recommended tasks:** Список следующих логичных задач (каждая на ~одну рабочую сессию).
6. **Platform boundaries:** Для каждого модуля фиксируй его принадлежность (`Core`, `Web`, `Desktop`, `Backend`, `Shared`), чтобы в дальнейшем не нарушать архитектуру.

## Строгие запреты

Во время миграции запрещается:

- Выполнять массовые переименования без причины.
- Менять стиль проекта, форматирование всего проекта или линтер.
- Менять архитектуру вне рамок текущей задачи.
- Переносить файл "на будущее".
- Создавать временные решения (workarounds).

---

## Правило завершения сессии

Каждая рабочая сессия должна заканчиваться следующим состоянием:

1. Проект собирается, тесты и проверки проходят.
2. Архитектура стала проще.
3. `MIGRATION_WIKI.md` обновлен.
4. `ARCHITECTURE_DEBT.md` обновлен (если найден новый долг).
5. Следующая задача очевидна.
6. Следующий агент может продолжить работу без дополнительного контекста.
