# Backlog к новой Alpha

## Цель

По завершении этого набора задач можно обозначить новую **alpha-версию** проекта.

Главный фокус текущего этапа — стабильная работа Web и Desktop во время миграции. Поэтому приоритеты выстроены так:

1. Безопасность, сохранность данных и блокирующие ошибки.
2. Единое поведение Web и Desktop.
3. Регрессионная защита через E2E.
4. UI-консистентность и визуальные исправления.
5. Новые фичи — только после стабилизации.

> `P0` — блокирует alpha.
> `P1` — необходимо закрыть для уверенной alpha.
> `P2` — допустимо перенести, если не влияет на стабильность.
> `P3` — новые фичи после стабилизации alpha.

## P0 — безопасность, данные и критические сценарии

### Безопасность содержимого заметок

- [x] **FIX(BACKEND): защита содержимого заметок от исполнения вредоносного кода**
  - Проверить, существует ли защита сейчас.
  - Если её нет — добавить.
  - Пользователь должен иметь возможность сохранить любой текст, включая похожий на SQL, JavaScript или HTML.
  - При этом содержимое заметки не должно исполняться как код ни в Web, ни в Desktop.
  - Защита должна работать и в полноценном просмотре, и в превью айтема.

### Сохранение форматирования заметок

- [x] **FIX(WEB): сохранение форматирования заметки**
  - Форматирование не должно теряться после сохранения, открытия или перезагрузки страницы.
  - Поведение должно соответствовать Desktop-версии.

### Единое создание и редактирование заметки

- [x] **FIX(DESKTOP, WEB): при редактировании заметки использовать то же окно, что и при создании**
  - Использовать единый UI и общий набор компонентов.
  - Допускаются небольшие отличия, обусловленные контекстом: заголовок, начальные значения, доступные действия.
  - Цель — исключить расхождение поведения между созданием и редактированием.

### Предупреждение о несохранённых изменениях

- [x] **FIX(FRONT): подтверждение выхода при создании нового айтема**
  - При нажатии на иконочную кнопку «Назад» показать модальное окно.
  - Смысл: предупредить, что изменения могут быть потеряны, и уточнить, хочет ли пользователь выйти и выбрать другой тип содержимого.
  - При подтверждении:
    - сбросить все изменения общей формы создания айтема;
    - не переносить данные в новый тип контента;
    - исключить конфликты и смешение полей разных типов айтемов.

### Ограничение количества тегов

- [x] **FIX(BACKEND): ограничить количество тегов у айтема**
  - Ограничение должно быть определено отдельной константой.
  - Валидация обязательна на Backend, а не только на Frontend.
  - Frontend должен корректно отображать ошибку ограничения пользователю.

### Аудио без метаданных

- [x] **FIX(WEB): отображать корректное название аудиофайла в сетке айтемов**
  - Файл без метаданных не должен отображаться пустым или некорректным названием.
  - Использовать fallback: имя файла без расширения либо нейтральное системное название.

### macOS: системная верхняя панель

- [x] **FIX(DESKTOP MACOS): drag area для верхней системной полосы со «светофором»**
  - В области верхней системной панели должна быть drag area.
  - Фон должен соответствовать текущей светлой или тёмной теме.
  - Проверить взаимодействие с кнопками управления окном и контентом приложения.

## P1 — стабильность интерфейса и защита от регрессий

  Минимальные сценарии:

  - работа Electron-версии;

### Аудит использования кнопок

- [ ] **FIX(FRONT): проверить кнопки в интерфейсе**
  - Приоритет — использовать проектный `<Button />` вместо нативного `<button />` с локальной кастомизацией.
  - Проверить корректность:
    - стилей;
    - иконок;
    - размеров;
    - состояний disabled/loading;
    - доступности;
    - контекста применения.
  - Сначала пройти критические экраны: auth, dashboard, создание и редактирование заметки, просмотр айтема.
  - Не превращать задачу в полный бесконтрольный рефакторинг до alpha.

- [x] **FIX(FRONT): универсальное использование компонента TagEditor на вебе и десктопе**
  - Приоритет – использование компонента `<TagEditor />` как единую форму для создания тегов
  - Веб и десктоп предоставляют свой API для того, чтобы это сделать
  - На десктопе – локальное обращение(реализовать позже, оставить блок "В разработке" в настройках) или запрос на сервер(должна быть проверка, что статус аккаунта позволяет обрабатывать контент с помощью ИИ)

  - Требуется верно обрабатывать ошибки для данной универсальной формы

- [ ] **FIX(BACKEND): не создавать теги, если айтем по итогу не был сохранён**
  - Когда мы создаём айтем и выбираем на генерацию тегов, то они у нас создаются сразу в базе
  - ИИ должен выдавать только массив тегов, которые у нас так же могут быть в БД, т.е. не создавая дубликаты

- [x] **FIX(DESKTOP): использовать вместо desktopStrings, accountStrings и т.д. значения из i18n**
  - Сейчас в `main.tsx` используются какие-то кастомные строки, хотя единственная точка получения пользовательских строк в UI – это локализированный i18n
  - Это должно быть учтено по всем правилам правильного i18n
  - Как предложение, можно сделать i18n отдельным пакетом в `packages/`, чтобы можно было на самом деле делать этот пакет более независимым со своим словарём и утилитами под определённый язык

## P3 — фичи после стабилизации alpha

### Форматированное превью заметки в карточке

- [ ] **FEAT(FRONT): отображать форматирование заметки в `item.tsx`**
  - В превью заметки использовать то же форматирование, что и в полноценном просмотре.
  - Размер отображения — примерно на 25% меньше.
  - Корректно обрабатывать блочные элементы: кодовые блоки, цитаты, списки, таблицы и другие элементы, требующие закрытия структуры.
  - Не обрезать HTML/Markdown простым обрезанием строки: превью не должно ломать разметку.
  - Добавить символьное ограничение загрузки контента для превью.

### Поиск в просмотре заметки

- [ ] **FEAT(FRONT): поиск по содержимому заметки в режиме просмотра**
  - Открытие через `Cmd/Ctrl + F`.
  - Также доступ через меню с вертикальным троеточием.
  - Поиск должен работать внутри содержимого заметки и не конфликтовать с браузерным поиском.

### Поиск и замена в редакторе

- [ ] **FEAT(FRONT): поиск и замена текста при редактировании заметки**
  - Поиск по содержимому текущей заметки.
  - Замена одного совпадения.
  - Замена всех совпадений.
  - Не нарушать структуру и форматирование документа.

### Поддержка таблиц в заметках

- [ ] **FEAT(FRONT): поддержка таблиц в note item**
  - Проверить весь цикл:
    - создание таблицы в редакторе;
    - хранение;
    - отображение в Web;
    - отображение в Desktop;
    - отображение в полноразмерном просмотре;
    - корректное поведение в превью карточки.

### Закреплённые айтемы на dashboard

- [ ] **FEAT(FRONT + BACK): функционал закрепления айтемов**

  Базовый сценарий:

  - закрепить/открепить айтем через ПКМ;
  - на телефоне — через долгое нажатие;
  - внутри просмотра айтема — через меню с иконкой вертикального троеточия;
  - в строке фильтров рядом с поиском добавить активный по умолчанию icon-only фильтр с `pin`;
  - при выключении фильтра не показывать закреплённые айтемы в начале dashboard;
  - закреплённые айтемы должны быть доступны на странице тегов / Pinned.

  Рекомендуемая декомпозиция:

  - [ ] **v1:** pin/unpin, хранение статуса, отображение закреплённых в начале dashboard, фильтр pin.
  - [ ] **v1.1:** отдельная сетка закреплённых айтемов на странице Pinned в «Тегах».
  - [ ] **v2:** drag-and-drop закреплённых айтемов для изменения порядка.

  Для drag-and-drop:

  - хранить не только `itemId`, но и порядок закреплённых айтемов;
  - изменение порядка не должно ломать основную сортировку и обычный список;
  - продумать поведение при удалении, откреплении и появлении новых айтемов;
  - не включать в первую версию pin-функциональности без отдельной оценки.

## Definition of Done для новой Alpha

Новую alpha можно обозначить после выполнения `P0` и `P1`, если:

- содержимое заметок безопасно хранится и отображается;
- форматирование заметок не теряется;
- создание и редактирование работают одинаково в Web и Desktop;
- пользователь не теряет черновик из-за неочевидного выхода;
- теги валидируются на Backend;
- базовые ошибки отображения айтемов устранены;
- критические сценарии защищены E2E-тестами;
- нет известных блокирующих регрессий Web, Desktop и macOS-окна.

Все задачи из `P2` и `P3` не должны задерживать alpha, если они не выявляют новую проблему со стабильностью, безопасностью или потерей данных.
